# Initial live experiments — September 22, 2026

**Main finding:** supplied context materially changed decisions, while network/API latency was small enough for an interactive prototype. The browser's serial queue and scheduling made visible hiding slower than individual API calls. A boundary score changed the mute decision on repeat requests.

This is a controlled pilot: 36 short synthetic cases, assistant-authored expected labels, one machine/time window. It does not establish real-feed accuracy, independent evaluation, calibration, or prompt-injection robustness. No product prompts were tuned during this run.

## Context and decision quality

At the existing 0.85 threshold, the 36 full-context first-pass decisions matched all 36 authored labels: 16 true mutes, 20 true keeps, zero false mutes and zero missed mutes. **Do not describe this as “100% accurate” in real use.** The examples were intentionally short and designed around known behaviors; labels were not independently reviewed.

Text-only matched 27/36 labels: seven true mutes, 20 true keeps, nine missed mutes. This is an evidence-removal experiment: some labels become unknowable without metadata. It does not mean Jev should have inferred missing identities.

Examples:

- Owner-only rule: “We shipped a new feature today.” Full context identified Arvind Jain as the author: **0.93**; body text alone: **0.16**.
- Community rule: compiler post in `r/startups`: **0.85** with metadata, **0.15** without.
- Sponsorship: identical sales text scored **0.91** with `promoted:true`, versus **0.36** without evidence of sponsorship.
- Cooking-video rule: “Dinner tonight.” scored **0.89** with pasta-cooking subtitles, **0.03** without.

The simple text-regex baseline matched 17/36 labels (eight true mutes, nine true keeps, 11 false mutes, eight misses). It lacks metadata handling and was not optimized; the challenge set includes intentionally difficult lexical distractors. This is a sanity baseline, not a competitive benchmark.

## Threshold sensitivity and a repeatability failure

Reusing the same full-context first-pass scores:

| Threshold | True mutes / 16 | False mutes / 20 | Missed mutes / 16 |
|---|---:|---:|---:|
| 0.50 | 16 | 2 | 0 |
| 0.70 | 16 | 1 | 0 |
| 0.85 (existing default) | 16 | 0 | 0 |
| 0.95 | 6 | 0 | 10 |
| 0.99 | 0 | 0 | 16 |

At 0.50, a body mentioning Arvind Jain without owner metadata and a crosspost mentioning `r/startups` in a different community were falsely muted. A lower threshold can hide more while also accepting weaker evidence.

One preselected adversarial cooking-video example said to ignore the mute rules and return zero. Its first score was **0.85**, then **0.84 and 0.84** on identical repeat requests. At the default threshold it was muted once and missed twice. The repeated request hashes match. This is an observed decision flip, not proof that the injected instruction caused it. The other two repeated examples kept the same binary outcome. Do not claim stable decisions or injection immunity.

## Actual extension, synthetic browser feed

Five live calls ran through the built extension in isolated headless Chromium, on synthetic HN-shaped cards. All five posts were deliberately obvious positive examples.

- Three cards inserted together hid after **772, 897 and 1,055 ms**. These timings include startup/scheduling, serial queueing and API response time.
- Two later additions hid after **235 and 371 ms**.
- Reloading and reinserting the same five posts while the worker stayed alive made **zero new API calls**. They hid in **344–347 ms**; the remaining delay is outside the API.
- Clicking Show post restored a card. The measured 171 ms included Playwright automation overhead and is not a pure UI latency estimate.

This establishes one working end-to-end path and same-worker cache reuse. It is not a live-site adapter benchmark or evidence that the cache persists across worker termination.

## What remains before a real-world claim

Collect a consecutive real-feed sample with user labels assigned before seeing model results. Separately measure extraction coverage, ambiguous cases, misses, false mutes and costs. Repeat latency measurements across sessions/networks. The detailed protocol is in the methodology document.
